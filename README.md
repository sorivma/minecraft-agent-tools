# Minecraft Agent Tools

Серверный мод Forge 1.7.10 для передачи агенту состояния ванильного Minecraft через MCP.
Самостоятельный проект без зависимости от Minecraft Harness. Для серверных наблюдений
клиентский мод не требуется; необязательный доступ к NEI использует отдельный клиентский мод.

## Статус

Реализована первая версия чтения всех семи областей: игрок, окружение, сущности,
инвентарь, взаимодействие, изменения и игровые справочники. Есть внешний MCP stdio
процесс с загрузкой провайдеров из отдельных JAR и локальный TCP-мост с проверкой токена.
Ядро не содержит встроенных инструментов: Minecraft-инструменты поставляются в
`minecraft-tools.jar`. Добавлены NEI-провайдер `nei-tools.jar` и клиентский адаптер для
общего чтения предметов, рецептов и применений через обработчики NEI. Добавлены временные визуальные метки:
выделение сущностей и блоков, точки назначения и указатель направления через частицы.
Блоки, инвентари и положение игрока эти инструменты не изменяют.

Отдельный GregTech-модуль добавляет 12 инструментов чтения рецептов, машин, энергии,
доступных определений мультиблоков, материалов и ore prefixes.
Подключение и границы покрытия — в разделе [GregTech](#доступ-к-gregtech).

Сборка и изолированные тесты проверяются без запуска Minecraft. Работа на живом выделенном
сервере и клиенте с NEI пока не проверена: успешная сборка не заменяет эту проверку.
Автоматическое управление игроком и построение проходимых маршрутов не реализованы.

## Архитектура

`агент → core.jar (Java 21) → plugins/* → TCP loopback → Forge (Java 8) → серверный игровой поток`

- `bridge-protocol`: Java 8, фрейминг, сессии, границы сканирования,
  сравнение снимков. Нет зависимостей от Minecraft, MCP SDK или JSON-библиотек.
- `mcp-api`: Java 8, интерфейсы `ToolProvider` и `ToolContext`, без Minecraft, Gson и MCP SDK.
- `mcp-server`: Java 21, ядро JSON-RPC/MCP, загрузка JAR, маршрутизация и Gson 2.11.0.
  Не зависит от Minecraft-провайдера во время работы. Реализован профиль MCP 2025-11-25:
  initialize, notifications/initialized, ping, tools/list, tools/call.
- `minecraft-tools`: Java 8, отдельный провайдер: описания и проверка Minecraft-инструментов,
  инструкции агенту и маршрутизация в Minecraft-мост. Зависит от протокола и `mcp-api`.
- `forge-1.7.10`: Java 8, серверный адаптер. Использует Gson, уже поставляемый Minecraft;
  включает протокол и класс контракта `Tools` из `minecraft-tools`, но не его провайдер.
  Современный Gson, Java 21 и механизм загрузки MCP-провайдеров в JAR мода не попадают.
- `nei-tools`: Java 8, отдельный MCP-провайдер и общий контракт NEI без игровых зависимостей.
- `forge-nei-1.7.10`: Java 8, отдельный клиентский адаптер. Компилируется против NEI GTNH
  2.6.44, не включает NEI или MCP-провайдер в свой JAR и не зависит от GregTech.
  Свой TCP-мост направляет запросы на END клиентского тика.
- `gregtech-tools`: Java 8, отдельный MCP-провайдер и контракт GregTech без игровых зависимостей.
- `forge-gregtech-1.7.10`: Java 8, отдельный серверный адаптер публичного API GTNH GregTech.
- `game-bridge`: Java 8, ограниченный loopback-транспорт игровых адаптеров; Gson 2.2.4
  используется только при компиляции, при работе его предоставляет Minecraft.

Контракт MCP: [stdio](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports),
[tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

Сетевые потоки разбирают запросы и сериализуют отделённые от игры результаты. Обращения
к Minecraft выполняются на END серверного тика. Очередь ограничена 32 запросами;
обрабатывается не более четырёх за тик с проверкой бюджета 5 мс между запросами.
Это не жёсткий предел длительности одного запроса. Ожидание игрового потока — до 5 секунд.
Просроченные задания пропускаются; завершение сервера закрывает соединения и очередь.

## Сборка

### Пакеты и стиль кода

Исходники и тесты используют одинаковую структуру пакетов:

- `dev.minecraftagenttools.api` — независимый SPI провайдеров MCP.
- `dev.minecraftagenttools.protocol.transport` — фрейминг сообщений;
  `protocol.data` — общие структуры данных; `protocol.world` — сессии,
  снимки, области сканирования и метки.
- `dev.minecraftagenttools.mcp` — точка входа; `mcp.rpc` — JSON-RPC;
  `mcp.plugins` — загрузка и реестр провайдеров; `mcp.bridge` — соединения с адаптерами.
- `dev.minecraftagenttools.{minecraft,nei,gregtech}.contract` — контракты Java 8;
  соответствующие пакеты `.provider` — реализации MCP-провайдеров.
- `dev.minecraftagenttools.forge.{minecraft,nei,gregtech}` — игровые адаптеры;
  `dev.minecraftagenttools.gamebridge` — их общий транспорт.

Java-код форматируется Google Java Format в стиле AOSP (отступ 4 пробела),
Gradle Kotlin DSL — ktfmt. Версии форматтеров закреплены в корневой сборке.
Общие настройки редакторов находятся в `.editorconfig`.

```powershell
.\gradlew.bat spotlessApply # Применить форматирование
.\gradlew.bat spotlessCheck # Проверить форматирование
```

`build` и `check` также проверяют форматирование. Локальная конфигурация агента,
токены окружения, игровые каталоги и результаты сборки исключены из Git.

### Команды сборки

Gradle Wrapper 8.8 запускается на JDK 21, адаптер и протокол компилируются Java 8 toolchain.

```powershell
.\gradlew.bat build :mcp-server:installDist
```

Результаты:

- Готовый набор: `build/bundle/core.jar`, `build/bundle/plugins/minecraft-tools.jar`
  и серверный мод в `build/bundle/forge/`. Этот набор собирается также командой `gradlew.bat bundle`.
- Самостоятельное ядро со всеми своими зависимостями:
  `mcp-server/build/libs/minecraft-agent-tools-core-0.1.0-SNAPSHOT.jar`.
- Отдельный провайдер: `minecraft-tools/build/libs/minecraft-tools-0.1.0-SNAPSHOT.jar`.
- Мод: `forge-1.7.10/build/libs/minecraft-agent-tools-forge-1.7.10-0.1.0-SNAPSHOT.jar`.
- MCP-дистрибутив: `mcp-server/build/install/mcp-server/`, включая `bin`, `lib` и `plugins`.
- Отчёты тестов: `bridge-protocol/build/reports/tests/test/index.html`,
  `minecraft-tools/build/reports/tests/test/index.html`,
  `mcp-server/build/reports/tests/test/index.html`.

## Необязательные провайдеры

```text
build/bundle/
  core.jar
  plugins/
    minecraft-tools.jar
  forge/
    minecraft-agent-tools-forge-1.7.10-0.1.0-SNAPSHOT.jar
```

MCP-клиент запускает `java -jar C:/path/to/bundle/core.jar`. Ядро автоматически ищет
`plugins` рядом с собой; в `installDist` — рядом с каталогом `lib`.
Другой каталог можно указать через `--plugins C:/path/to/plugins` или `MAT_PLUGINS`;
аргумент командной строки имеет приоритет. Относительный путь считается от рабочей папки процесса.
Поддерживается один уровень `*.jar` без рекурсивного обхода.

Если JAR присутствует, его инструменты добавляются в `tools/list` и направляются
его провайдеру. Если JAR убрать, после перезапуска MCP его инструменты исчезнут.
Пустой или отсутствующий `plugins` допустим: ядро запускается с пустым списком инструментов,
без токена и без подключения к Minecraft. Провайдеры загружаются только при старте;
изменение каталога требует перезапуска/переподключения MCP. Ошибочный провайдер,
несовместимая версия классов, повторяющийся ID провайдера или имя инструмента
останавливают запуск с ошибкой в stderr, без частичной регистрации.

JAR провайдера кладётся в `plugins` внешнего MCP-процесса. Серверный Forge-мод кладётся
в Minecraft `mods`. Это разные каталоги и процессы. Текущему Minecraft-провайдеру
нужен соответствующий Forge-мод; отсутствие работающего моста возвращает ошибку
конкретного инструмента, не мешая MCP обнаружить провайдеры.
`MAT_TOKEN` и `MAT_PORT` проверяются при вызове Minecraft-инструмента.

Новый тип интеграции, например NEI, добавляется отдельным провайдером по интерфейсу
[ToolProvider](mcp-api/src/main/java/dev/minecraftagenttools/api/ToolProvider.java).
JAR содержит файл `META-INF/services/dev.minecraftagenttools.api.ToolProvider`
с полным именем класса, реализующего этот интерфейс и имеющего публичный конструктор без аргументов.
Провайдер предоставляет ID, описания инструментов, их проверку и вызов; ядро менять не нужно.
Зависимости ядра и `mcp-api` в провайдер не включаются. Дополнительные зависимости можно
положить рядом в `plugins`; они разделяют один загрузчик классов, изоляции версий нет.
Конструктор, `tools()` и `instructions()` не обращаются к игре и не пишут в stdout.
Результат `call` — JSON-совместимая карта с `ok: true, data: ...` или `ok: false, error: ...`.
Строковые имена инструментов уникальны для всего endpoint; проверка аргументов лежит на провайдере.
Интерфейс Java 8 позволяет делать общие контракты с адаптерами; сам провайдер внешнего
процесса может использовать Java 21. Он не должен обращаться к игровым объектам напрямую.
Для loopback-моста есть `ToolContext.callBridge`: соединение `minecraft` использует
`MAT_TOKEN/MAT_PORT`, остальные имена — `MAT_<ИМЯ>_TOKEN` и `MAT_<ИМЯ>_PORT`.
NEI-провайдер использует отдельный клиентский адаптер, описанный ниже.

## Подключение

Для NEI см. [подключение клиентского адаптера](#доступ-к-nei).

1. Пользователь копирует JAR мода в `mods` выделенного Forge-сервера 1.7.10 и запускает его.
2. В `config/minecraftagenttools.cfg` автоматически создаются `bridge.port` (25576)
   и `bridge.token`. Токен предоставляет административный доступ к наблюдениям за всеми
   игроками, включая скрытые контейнеры и seed. Не публикуйте этот файл.
3. MCP-процесс запускается на том же компьютере. В его окружении задаются `MAT_TOKEN`
   из конфигурации мода и при необходимости `MAT_PORT`. Для нескольких серверов нужны
   разные порты и отдельные записи MCP. Мост слушает только loopback.
4. MCP-клиент запускает Java 21 с `core.jar`; рядом находится `plugins/minecraft-tools.jar`. Пример записи ниже;
   замените пути и токен. Это конфигурация клиента, не команда для запуска в игровом чате.

```json
{
  "mcpServers": {
    "minecraft": {
      "command": "C:/path/to/jdk-21/bin/java.exe",
      "args": [
        "-jar",
        "C:/path/to/minecraft-agent-tools/build/bundle/core.jar"
      ],
      "env": {
        "MAT_PORT": "25576",
        "MAT_TOKEN": "copy-the-generated-server-token-here"
      }
    }
  }
}
```

Stdout содержит только MCP JSON. Размер строки протокола ограничен 4 Mi символов.
Не запускайте MCP через Gradle в stdio-конфигурации: вывод Gradle не является MCP.

### Codex, в том числе чат внутри Minecraft

Для Codex используется TOML, а не JSON выше. Добавьте регистрацию в пользовательский
`%USERPROFILE%/.codex/config.toml` (либо `config.toml` фактически используемого
`CODEX_HOME`). Пример с путями-заглушками:

```toml
[mcp_servers.minecraft]
command = "C:/path/to/jdk-21/bin/java.exe"
args = ["-jar", "C:/path/to/bundle/core.jar"]
enabled = true

[mcp_servers.minecraft.env]
MAT_PORT = "25576"
MAT_TOKEN = "copy-the-generated-server-token-here"
```

Токен нужно взять из конфигурации именно запущенного экземпляра Forge. Не сохраняйте
реальный токен в репозитории. Копия конфигурации в произвольной папке `codex-home`
не подключается автоматически: процесс должен использовать эту папку как `CODEX_HOME`.
Игровой чат может запускать Codex из рабочей папки сохранения, поэтому настройка MCP
только в `.codex/config.toml` репозитория этого мода не обеспечивает доступ из игры.

Из рабочей папки игрового чата выполните `codex mcp list`: в списке должен появиться
включённый `minecraft`. Это проверяет регистрацию, но не соединение с игрой.
После изменения конфигурации переподключите игровой Codex и создайте новый диалог.
В Minecraft Harness доступны `/connect`, `/new` и `/mcp`; затем попросите агента
вызвать `list_sessions`. Это настройка внешнего клиента, зависимости от Harness нет.

## Инструменты

Следующие инструменты доступны только при установленном `minecraft-tools.jar`.

Сначала вызвать `list_sessions`. Он возвращает UUID онлайн-игроков, загруженные измерения
и их сессии. Все остальные инструменты требуют `session`, `dimension`, `player` (UUID).
Игрок должен находиться в указанном измерении. Перезапуск сервера, пересоздание мира или
смена измерения требуют повторного обнаружения. Сессии действуют только в памяти.

| Инструмент | Данные и параметры сверх обязательных |
|---|---|
| `list_sessions` | Экземпляр сервера, измерения, сессии, игроки, доступные инструменты |
| `observe` | Игрок, среда, инвентарь, цель луча, сущности; `radius` 1–64 (16), `limit` 1–256 (64) |
| `get_player_context` | Координаты, движение, взгляд, здоровье, голод, броня, эффекты, опыт, режим, погода, время, seed, блоки у ног |
| `get_inventory` | 36 основных слотов + броня, выбранный слот, переносимый стек, эндер-сундук, открытый контейнер |
| `get_interaction` | Серверное приближение цели взгляда, дальность, серверный открытый контейнер |
| `list_entities` | Загруженные сущности в сфере вокруг игрока; `radius` 1–64 (16), `offset` (0), `limit` 1–256 (64) |
| `inspect_entity` | `entityId`: состояние, экипировка, эффекты, NBT сущности |
| `inspect_block` | `x`, `y` 0–255, `z`: блок, metadata, свет, биом, высота, свойства, NBT tile entity, содержимое закрытого контейнера |
| `read_terrain` | Компактная карта блоков вокруг игрока, расположение контейнеров/tile entities и сущности; по умолчанию 3×3 чанка и Y игрока ±8; `chunkX/chunkZ`, `chunkRadius` 0–2 (1), `minY/maxY` 0–255, `offset`, `tileOffset`, `entityOffset` |
| `scan_area` | `minX/minY/minZ`, `maxX/maxY/maxZ`, `offset` (0), `limit` 1–512 (256); включительные границы, максимум 32768 ячеек |
| `get_changes` | `radius` 1–4 (2), необязательный `cursor`; различия снимков игрока, инвентаря, погоды, сущностей и блоков |
| `get_registry` | `kind`: `items` или `blocks`; `offset` (0), `limit` 1–256 (64) |
| `highlight_entity` | `entityId`, `entityUuid`: временная метка, следующая за мобом или выпавшим предметом |
| `highlight_block` | `x`, `y` 0–255, `z`: временная метка блока |
| `set_waypoint` | `x`, `y` 0–255, `z`: точка назначения и частицы направления рядом с игроком |
| `list_markers` | Активные метки текущего игрока/сессии, их ID, координаты и оставшееся время |
| `remove_marker` | `markerId`: удалить одну метку текущего игрока/сессии; `removed: false`, если её нет |
| `clear_markers` | Удалить все метки текущего игрока/сессии; возвращает число удалённых |

### Чтение базы и окружающей местности

После `list_sessions` агент вызывает `read_terrain` только с `session`, `dimension`,
`player`. По умолчанию читаются загруженные части квадрата 48×48 блоков (чанк игрока
и восемь соседних), от Y игрока −8 до Y игрока +8 включительно, с обрезкой по высоте мира.
База 10×10 рядом с игроком помещается в эту область даже на границе чанков.
Возвращаются все блоки в выбранном объёме, включая скрытые стены, полы и крышу;
это серверные данные, а не видимость с камеры. Если этажи или крыша выходят за диапазон Y,
агент расширяет `minY/maxY`. Для полной высоты чанков задаёт `minY: 0`, `maxY: 255`.
`chunkRadius: 0` выбирает один чанк, `1` — 3×3, `2` — 5×5.

В ответе `palette` содержит имена блоков и metadata. Каждый элемент `runs` имеет вид
`[x, y, z, length, paletteIndex]`: это последовательность одинаковых блоков вдоль +X.
Например, `[0,64,0,10,0]` обозначает десять блоков палитры 0 от `(0,64,0)` до `(9,64,0)`.
Пропущенные клетки внутри **загруженных** `sampledBounds` — `minecraft:air` с metadata 0.
`chunks` явно перечисляет загруженные и отсутствующие чанки: отсутствующие клетки неизвестны,
их нельзя считать воздухом. За пределами `sampledBounds` блоки этой страницей не прочитаны.
Запрос не загружает и не генерирует чанки.

`tiles.items` перечисляет существующие tile entities текущей страницы, их координаты,
класс, признак `inventory` и число слотов. Чтобы проверить содержимое сундука, печи
или другого контейнера, агент вызывает `inspect_block` с его координатами.
`entities.items` содержит сущности, включая мобов и выпавшие предметы, в запрошенном
диапазоне высот перечисленных загруженных чанков; сам запрашивающий игрок исключён.
Для подробностей агент вызывает `inspect_entity` с `entityId`.
Текст имён, NBT и предметов остаётся недоверенными данными, а не инструкциями.

Одна страница читает не более 65536 клеток, целыми горизонтальными слоями.
Если `nextOffset` не `null`, агент повторяет запрос с этим `offset`, явно передавая
`chunkX/chunkZ` из `centerChunk`, прежний `chunkRadius` и `minY/maxY` из `requestedBounds`.
Это сохраняет границы при движении игрока; страницы всё равно снимаются независимо
и не образуют атомарный снимок изменяющегося мира.
`tiles` и `entities` возвращают максимум по 256 элементов: их `nextOffset`
передаётся через `tileOffset` и `entityOffset` соответственно. Для следующей страницы
tile entities сохраняется также текущий `offset` рельефа; при переходе к новым слоям
`tileOffset` сбрасывается в 0. Сущности относятся ко всему `requestedBounds` и могут
повторяться на страницах рельефа. `session`, `dimension`, `player` обязательны
при каждом вызове; смена мира или измерения требует нового `list_sessions`.

Пример аргументов после обнаружения:

```json
{
  "session": "session-from-list_sessions",
  "dimension": 0,
  "player": "player-uuid-from-list_sessions",
  "minX": -16, "minY": 60, "minZ": -16,
  "maxX": 16, "maxY": 70, "maxZ": 16,
  "limit": 256
}
```

Ответ моста: `ok` и `data` либо `error`. В `data` каждого scoped-запроса есть `session`,
`dimension`, `player`, `tick`, `observedAtEpochMs`, `result`. MCP возвращает его одновременно
как текст и `structuredContent`; ошибки моста имеют `isError: true`.

## Временные метки и точки назначения

У трёх инструментов создания есть необязательный `durationSeconds`: 1–120 секунд,
по умолчанию 10. Срок измеряется монотонными часами; истёкшие метки удаляются на
следующем серверном тике. Разрешено до 8 меток на игрока в сессии измерения и 256
на сервер. Новая цель должна находиться в загруженном чанке не дальше 64 блоков.
Повторное создание добавляет отдельную метку; ответ содержит `markerId` для удаления.

Частицы видит только указанный игрок; клиентский мод не нужен. Зелёное кольцо
появляется над целью и обновляется каждые 10 тиков. У точки назначения дополнительно
появляется короткая линия направления от игрока. Координаты X/Z обозначают центр
указанного блока. Можно поставить несколько точек последовательными вызовами.
Это визуальные ориентиры: линия не учитывает стены, опасности и проходимость,
игрок движется сам. Текст чата не используется как источник команд.

Пример `highlight_entity` (значения scope и цели взять из `list_sessions` и `list_entities`;
поле `uuid` сущности передать как `entityUuid`):

```json
{
  "session": "session-from-list_sessions", "dimension": 0,
  "player": "player-uuid-from-list_sessions",
  "entityId": 123, "entityUuid": "entity-uuid-from-list_entities",
  "durationSeconds": 15
}
```

Для `set_waypoint` вместо `entityId/entityUuid` передать `x`, `y`, `z`.
Метки снимаются при выходе игрока, смерти, смене измерения/объекта игрока, выгрузке
мира или чанка цели, исчезновении сущности. Старый ID сущности не подменяет цель:
при создании проверяется UUID, затем сохраняется точный объект сущности.
После перехода в другой мир нужны новое обнаружение и новые метки.

Отрисовка зависит от настроек частиц и дальности клиента; это не контур сквозь стены
и не постоянная HUD-метка. За пределами 64 блоков отправка частиц приостанавливается,
но срок жизни продолжает идти. Уже отправленные частицы исчезают по своим ванильным
правилам, поэтому после удаления возможен короткий визуальный остаток.
Если ответ создания потерян из-за разрыва соединения, сначала проверить `list_markers`,
чтобы повторным вызовом не создать дубликат.

## Границы достоверности

- Чанки не загружаются и не генерируются запросами. Незагруженная ячейка явно имеет
  `availability: chunk_unloaded`, а не воздух. Произвольное загруженное место можно
  обследовать по координатам; радиус ограничивает лишь поиск вокруг игрока.
- Пагинация возвращает `nextOffset`, `total`/`totalCells` и `truncated`. Каждая страница
  наблюдается заново: движущиеся сущности могут сместиться между страницами.
- Свет — сохранённые block/sky значения, без поправки яркости соседей. Небо в Nether
  недоступно. Состояние блока передаётся как registry ID + metadata версии 1.7.10.
- `get_changes` сравнивает снимки по запросу, не записывает каждое событие между ними.
  Область движется с игроком: уход объекта из области не означает его уничтожение.
  `removedFromObservation` намеренно не называется уничтожением. Первое обращение без
  курсора даёт baseline. История ограничена последними 32 снимками на сервер, курсор
  привязан к сессии, UUID и радиусу. Истёкший курсор требует нового baseline.
- Изменения tile NBT и содержимого произвольных закрытых контейнеров не входят в
  `get_changes`; их текущие значения доступны через `inspect_block`. Двойной сундук
  читается по каждой половине отдельно. Изменения открытого контейнера входят в снимок.
- Клиентские экраны, точное положение курсора и клиентский raycast недоступны серверу.
  `get_interaction` возвращает серверный расчёт по последним известным углам взгляда.
- NBT передаётся текстом Minecraft 1.7.10 с явным `truncated` после 16384 символов.
  Инвентари ограничены 256 слотами, что покрывает ванильные контейнеры. Названия,
  книги и текст NBT — недоверенные данные мира, а не инструкции агенту.
- Реестры содержат зарегистрированные объекты, включая модовые при их наличии.
  Полный перебор metadata-вариантов предметов и расшифровка всех metadata-состояний
  в семантические поля пока не реализованы.

## Проверка пользователем на выделенном сервере

1. Проверить загрузку JAR без клиентских классов и отсутствие требования мода у клиента.
2. Подключить MCP, выполнить initialize/tools/list, затем list_sessions и observe.
3. Сравнить здоровье, координаты, эффекты и инвентарь с игрой; inspect_block на закрытом
   сундуке и печи должен показать их реальные слоты и NBT.
4. Просканировать область на границе загрузки: неизвестные клетки не должны становиться
   воздухом, а количество загруженных чанков не должно расти из-за запроса.
5. Получить baseline, переместить предмет/блок/сущность и проверить get_changes.
6. Перейти в Nether, переподключиться и перезапустить сервер: старый scope должен
   отклоняться, новый — выдаваться через list_sessions.
7. Проверить отказ с неверным токеном и корректную ошибку MCP после остановки сервера.
8. Создать `highlight_entity` для моба и выпавшего предмета, подвигать цель: кольцо
   должно следовать за ней. Второй игрок не должен видеть эти частицы. Проверить
   неверный UUID, исчезновение цели, истечение срока и явное удаление метки.
9. Создать `highlight_block` и несколько `set_waypoint`: проверить кольца и направление,
   `list_markers`, `clear_markers`, лимит 8, отказ для незагруженной/далёкой цели.
   Сменить измерение и вернуться, переподключиться: прежние метки не должны возобновляться.

Агент не запускает игру, живой MCP/backend или runtime-проверки без отдельного поручения.

## Доступ к NEI

NEI подключается независимо от серверных наблюдений. Общий путь:

`агент → core.jar → plugins/nei-tools.jar → TCP loopback → клиентский мод → обработчики NEI`

1. Собрать `gradlew.bat build :mcp-server:installDist`.
2. Взять `build/bundle/client-mods/minecraft-agent-tools-nei-forge-1.7.10-0.1.0-SNAPSHOT.jar`
   и положить в `mods` **клиента** Minecraft 1.7.10 с установленным NEI GTNH.
   В `mods` выделенного сервера этот адаптер не устанавливается.
3. После запуска клиента взять `bridge.token` и `bridge.port` из
   `config/minecraftagenttoolsnei.cfg`. Порт по умолчанию — 25577.
4. В окружении внешнего MCP-процесса задать `MAT_NEI_TOKEN` и `MAT_NEI_PORT`.
   Для NEI оба значения обязательны; `MAT_TOKEN/MAT_PORT` относятся к другому, серверному мосту.
5. Оставить `nei-tools.jar` в `build/bundle/plugins` и подключить `core.jar` обычным способом.
   Для доступа только к NEI можно убрать `minecraft-tools.jar`. После удаления `nei-tools.jar`
   и перезапуска MCP все `nei_*` инструменты исчезают.

Библиотека компиляции — `com.github.GTNewHorizons:NotEnoughItems:2.6.44-GTNH:dev`
из Maven GTNH, Java 8. NEI и его зависимости пользователь устанавливает обычным способом;
они не включаются в наши JAR. Исходники API:
[IRecipeHandler](https://github.com/GTNewHorizons/NotEnoughItems/blob/2.6.44-GTNH/src/main/java/codechicken/nei/recipe/IRecipeHandler.java),
[ICraftingHandler](https://github.com/GTNewHorizons/NotEnoughItems/blob/2.6.44-GTNH/src/main/java/codechicken/nei/recipe/ICraftingHandler.java),
[IUsageHandler](https://github.com/GTNewHorizons/NotEnoughItems/blob/2.6.44-GTNH/src/main/java/codechicken/nei/recipe/IUsageHandler.java).
Оригинальный NEI и более старые форки не заявлены совместимыми. Более новые версии GTNH
могут использовать этот API, но нуждаются в проверке на конкретной сборке игры.

Рабочая последовательность для агента:

| Инструмент | Аргументы и результат |
| --- | --- |
| `nei_status` | `{}` → `session`, `dimension`, `ready`, размер каталога и возможности |
| `nei_list_handlers` | `session`, `dimension`, необязательные `offset`, `limit` → обработчики, поддержка `recipes`/`usages`, `nextOffset` |
| `nei_search_items` | `session`, `dimension`, `query`, необязательные `offset`, `limit` → предметы с `itemId`, `nextOffset` |
| `nei_find_recipes` | `session`, `dimension`, `handler`, `itemId`, `mode: recipes` или `usages` → `queryId`, `recipeCount` |
| `nei_get_recipe` | `session`, `dimension`, `queryId`, `recipeIndex` от 0 → ингредиенты с альтернативами, основной результат, дополнительные стеки |

После `nei_status` нужно дождаться `ready: true`. NEI-сессия принадлежит клиентскому миру;
она отличается от `session` серверных инструментов, полученной через `list_sessions`.
Scoped-ответы имеют `data.session`, `data.dimension`, `data.observedAtEpochMs`, `data.result`.
Статус возвращает поля непосредственно в `data`.

Поиск — буквальная подстрока без учёта регистра в registry name или локализованном имени,
а не синтаксис строки поиска NEI. Один запрос просматривает не больше 512 записей каталога,
проверяя бюджет 4 мс между предметами; `limit` — 1–64, по умолчанию 32.
Даже пустая страница может иметь `nextOffset`: нужно продолжать с этим смещением и тем же `query`.
Ошибки отдельных предметов возвращаются в `errors`. Поиск не меняет фильтр или GUI NEI.

Список обработчиков включает обе группы регистрации NEI: обычную и serial.
Для поиска рецептов выбирается один `handler` из обнаруженного списка. Чтобы проверить
все плагины, агент обходит обработчики отдельными вызовами. Вызываются
`getRecipeHandler("item", stack)` и `getUsageHandler("item", stack)`; любые моды и аддоны,
зарегистрировавшие совместимый обработчик, доступны через этот общий путь.
Переходы по катализаторам, открытие GUI, перенос ингредиентов и автокрафт не выполняются.

`itemId` — непрозрачный идентификатор копии предмета, включая его NBT; хранится не более
2048 таких копий, срок — до 5 минут. `queryId` хранит результат обращения к обработчику:
до 16 запросов, срок — до 60 секунд. При заполнении вытесняются старые записи.
Страницы рецептов читаются из экземпляра обработчика, это не гарантированный неизменяемый
снимок внутреннего состояния стороннего плагина. При истечении срока нужно повторить поиск.
При смене мира, измерения, отключении или замене/перезагрузке каталога NEI все идентификаторы
и сессия аннулируются. Запрос, ожидавший в очереди до перехода, проверяет scope перед выполнением.

Рецепт содержит до 64 слотов в каждой группе и до 32 альтернатив в слоте; количество
и признаки усечения возвращаются явно. NBT представлен строкой SNBT до 8192 символов
с `nbtTruncated`; это описание, а не вход для выполнения команд. Количества, metadata,
альтернативы и координаты слотов сохраняются. Основной результат может отсутствовать.
`otherStacks` сохраняются с ролью `unspecified`: среди них могут быть топливо, побочные
продукты или декоративные предметы. Нельзя считать их все выходами рецепта.

Общий API NEI не гарантирует структурированные жидкости, EU/t, время, вероятности
и условия машины. Адаптер сообщает недоступность этих полей, не подставляя нули и не
пытаясь распознать нарисованный текст. Специальных зависимостей или ветвлений для GregTech нет.

Сетевой ввод-вывод и Gson работают вне игрового потока. Очередь ограничена 32 заданиями,
за клиентский тик выбирается до четырёх с проверкой бюджета 5 мс между заданиями.
Один вызов стороннего обработчика синхронный: этот бюджет не является жёстким ограничением
его длительности. Ожидание очереди — до 5 секунд; просроченные задания пропускаются.
Результат больше лимита фрейма 4 Mi символов заменяется ошибкой о размере.

Изолированные тесты проверяют контракт, отзыв сессий/идентификаторов, маршрутизацию
опционального JAR, аутентификацию моста, исполнение на потоке тика и вызов подставного
стороннего обработчика NEI. Игра при этом не запускается.

Проверка пользователем на целевой сборке: дождаться `ready`, найти предмет, получить
его рецепты и применения из обычного и serial обработчика, сравнить с NEI вручную;
проверить альтернативы/NBT и отказ старых `session`/`itemId`/`queryId` после смены мира
или измерения. Живая совместимость с конкретными версиями GregTech и аддонов пока не проверена.

## Доступ к GregTech

Профиль публичных полей и методов сверён с GT5-Unofficial `5.09.54.183` и StructureLib
`1.4.45` из [манифеста GTNH 2.9.0-RC-1](https://github.com/GTNewHorizons/DreamAssemblerXXL/blob/master/releases/manifests/2.9.0-RC-1.json).
В ветке 2.9.0 есть разные предварительные сборки: beta-3 использует GT `5.09.54.133`
и StructureLib `1.4.42`. `gt_status` сообщает установленную версию и доступность реестров.
Совместимость конкретного набора JAR нужно проверить в игре.

1. Собрать `gradlew.bat build :mcp-server:installDist`.
2. Оставить `build/bundle/plugins/gregtech-tools.jar` рядом с другими провайдерами.
   Он независим от `minecraft-tools.jar` и `nei-tools.jar`; после удаления его JAR и
   перезапуска MCP инструменты `gt_*` исчезают.
3. Установить JAR из `build/bundle/gregtech-mods` в `mods` сервера GTNH;
   для одиночной игры — в `mods` клиента с интегрированным сервером.
4. После запуска взять токен/порт из `config/minecraftagenttoolsgregtech.cfg` и задать
   `MAT_GREGTECH_TOKEN`, `MAT_GREGTECH_PORT` в окружении внешнего MCP. Порт — 25578 по умолчанию.
   Для удалённого сервера процесс MCP должен иметь локальный доступ к его loopback-мосту.
5. Начать с `gt_status`, затем передавать `session`, `dimension` из нужного элемента
   `dimensions`. Эти сессии независимы от NEI и серверных наблюдений.

| Инструмент | Данные |
| --- | --- |
| `gt_status` | Версия, сессии миров, доступность реестров, покрытие и ограничения |
| `gt_list_recipe_maps` | Карты рецептов, включая топливо и совместимые аддоны |
| `gt_search_recipes` | Поиск в карте по registry name предмета/жидкости, metadata и направлению input/output/either |
| `gt_get_recipe` | Предметы, альтернативы, жидкости, вероятности, EU/t, длительность, специальный слот/value и метаданные |
| `gt_list_machines` | Поиск метатайлов по имени/классу, ID машин и признак стандартного мультиблока |
| `gt_get_machine` | Описание, предмет машины, карта рецептов, публичные свойства и энергетические ограничения |
| `gt_get_structure` | Части StructureLib, локальные координаты элементов и доступные описания требований |
| `gt_inspect_machine` | Загруженная машина: энергия/пар, напряжение/амперы, средний I/O, состояние, прогресс, инвентарь, баки, NBT, люки |
| `gt_list_materials` / `gt_get_material` | Формула, свойства, топливные параметры, состав, побочные продукты, цели переработки, жидкие формы |
| `gt_list_ore_prefixes` | Имена и публичные свойства ore prefixes |
| `gt_get_energy_tiers` | V, VP, VN, VOLTAGE_NAMES установленного GregTech |

Все инструменты, кроме статуса, требуют scope. Обёртка ответа: `data.session`,
`data.dimension`, `data.tick`, `data.observedAtEpochMs`, `data.result`.
Статус возвращает поля непосредственно в `data`. Обращения выполняются на END серверного
тика, scope повторно проверяется перед выполнением. Чанки не загружаются:
незагруженная цель возвращает `chunk_unloaded`.

Пример после обнаружения карты через `gt_list_recipe_maps`:

```json
{
  "session": "from-gt_status", "dimension": 0,
  "map": "map-from-gt_list_recipe_maps",
  "item": "minecraft:iron_ingot", "direction": "output", "limit": 16
}
```

Поиск выдаёт `catalogId` со стабильными индексами. Для продолжения сохранить карту,
фильтры и `catalogId`, передать `nextOffset`; даже пустая страница может иметь продолжение.
Для деталей — `gt_get_recipe` с тем же scope, `catalogId`, `recipeIndex`.
Каталоги живут до 60 секунд; не более четырёх каталогов, до 200000 ссылок на рецепты
в каждом. Старые вытесняются; выгрузка/повторная загрузка мира отзывает их вместе со scope.
Это снимок списка ссылок, не глубокая копия изменяемых рецептов.
Списки/поиск просматривают до 512 записей, возвращают до 64 (по умолчанию 32), проверяют
бюджет 4 мс между записями; ошибки отдельных записей видны в `errors`. Создание снимка
списка и отдельный сторонний getter могут занимать больше этого бюджета.

У рецепта `energy.baseEUPerTick`, `durationTicks` — исходные параметры до разгона,
параллелей и эффективности машины. `baseEUtTimesTicks` — их точное произведение.
Вероятности читаются через четыре отдельных getter GregTech, масштаб — 10000.
Непотребляемый вход с вероятностью 0 всё равно может быть обязателен для запуска.
Доступные `mOreDictAlt`, `mAltFluidInputs` сохраняются; поиск учитывает их и wildcard metadata.
`mSpecialValue` имеет смысл, заданный картой: нельзя автоматически считать его EU,
температурой или давлением. Метаданные сохраняют идентификатор ключа и доступное
представление значения. Для неподдерживаемых объектов выдаются тип и публичные
скалярные поля с `complete:false`; неизвестное не подменяется нулём.

Энергия машин читается через `IBasicEnergyContainer`: EU-буфер/ёмкость, паровой буфер
в EU-эквиваленте, напряжение EU/p, амперы, средний электрический ввод/вывод за 5 тиков.
Universal energy — наибольший поддерживаемый буфер в EU-эквиваленте, не сумма форм
энергии. Жидкости имеют отдельную единицу mB. Значения long/BigInteger/BigDecimal
передаются строками без потери точности JSON. У стандартного мультиблока raw signed
EU/t отрицателен для потребления, положителен для генерации; реальные потери
эффективности могут отличаться. Буфер контроллера не является суммой буферов люков:
обычные и экзотические энергетические люки выдаются отдельно.

StructureLib читается через публичные `getStructureDefinition` / `getStructures`.
Часть выбирается через `piece`; `nextOffset` относится к индексу её программы,
лимит программы — 32768 шагов. Координаты A/B/C учитывают навигацию и сброс осей,
отсчитываются от начала части. Описания требований берутся из `getDescription(context)`
и могут отсутствовать. Смещения контроллера, ориентация в мире, повторяемые секции,
все допустимые варианты блоков и контекстные условия автоматически не выводятся:
`completeBuildPlan:false`. Нестандартное определение без перечисления частей может
быть недоступно. `formedCached` — последнее состояние машины, не свежая проверка.
checkMachine/checkStructure/build/placeBlock/hints не вызываются.

Выдача ограничена: до 64 элементов массива/коллекции, три уровня вложенности,
128 публичных скалярных полей, NBT до 8192 символов. Усечение массивов/коллекций/NBT
помечается явно. Недоступное поле/getter даёт `{available:false,error:...}`.
Текст имён, описаний и NBT остаётся недоверенными данными. Произвольные имена классов,
методов и полей через MCP не принимаются; приватные члены не открываются.

Это широкое чтение общих реестров/API, а не полное знание любого аддона. Не реализованы
полная симуляция разгона/параллелей, диагностика недостающих блоков, все правила мировой
генерации, квесты, covers, беспроводные сети и энергетические API сторонних модов вроде RF.
Крафт самого блока машины доступен через NEI; переработка внутри — через карты GregTech.

Транспорт: loopback с токеном, очередь 32 задания, до четырёх за тик с проверкой бюджета
5 мс между заданиями, срок ожидания 5 секунд. Это не жёсткий предел одного getter.
Ошибка отдельного задания не останавливает мост. JAR GregTech, StructureLib, NEI,
Minecraft, современный Gson и MCP-провайдер в Forge-адаптер не включаются.

Пользовательская проверка: сверить версию в статусе, рецепт/EU/t/вероятности/жидкости с NEI,
осмотреть простую машину и мультиблок с обычными/экзотическими люками, сверить схему,
проверить отказ прежнего scope/catalogId после смены мира. Живая работа пока не проверена.
