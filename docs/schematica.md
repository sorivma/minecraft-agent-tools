# Планы строительства через Schematica

Агент создаёт схемы с нуля: пол, проходы, группы машин, резерв под расширение.
Каждый план имеет своё имя, начало координат, палитру и набор прямоугольных областей.
До 32 планов отображаются одновременно; пользователь строит по призрачным блокам.
Реальные блоки и инвентари эти инструменты не меняют, принтер не используется.

## Подключение

- `schematica-tools.jar` — отдельный провайдер в `plugins` внешнего MCP.
- `minecraft-agent-tools-schematica-forge-1.7.10-*.jar` — клиентский адаптер в `mods`
  рядом со Schematica GTNH. Профиль публичного API сверён с установленной `1.12.6-GTNH`.
- Необязательный `minecraft-agent-tools-schematica-harness-1.7.10-*.jar` — виджет
  в `mods` рядом с адаптером и Minecraft Harness с callbacks в `WidgetCanvas`.
  Самостоятельные провайдер и адаптер от Harness не зависят.
- В `config/minecraftagenttoolsschematica.cfg`: `bridge.port` по умолчанию 25579,
  приватный `bridge.token`. В окружении MCP: `MAT_SCHEMATICA_PORT` и
  `MAT_SCHEMATICA_TOKEN` с такими же значениями.

Java 8 контракт и адаптер не включают MCP-провайдер, Harness, Schematica, GregTech
или современный Gson. Внешнее ядро работает на Java 21. Игровые операции выполняются
на клиентском потоке, TCP — на рабочих потоках общего `game-bridge`.

## Инструменты

| Инструмент | Действие |
| --- | --- |
| `schematic_status` | Готовность, клиентские session/dimension, ограничения |
| `schematic_list` | Все планы текущего мира, revision, видимость, ошибки отрисовки |
| `schematic_put` | Создать план или целиком заменить существующий по planId/revision |
| `schematic_get` | Получить полный план для последующего редактирования |
| `schematic_display` | Видимость, начало координат или один локальный слой; `layer: -1` — все слои |
| `schematic_remove` | Удалить призрачный план |
| `schematic_export` | Сохранить `.schematic` и исходный `.json` в `schematics` рабочего каталога MCP |

Все инструменты после статуса требуют **собственные** `session` и `dimension`
Schematica; сессии Minecraft, NEI и GregTech взаимозаменяемыми не являются.
Смена мира/измерения отзывает активные призраки и старые callbacks. Планы автоматически
сохраняются на клиенте и восстанавливаются по кнопке в чате после повторного входа.
Экспорт остаётся отдельным способом получить переносимые файлы; исходный JSON содержит
палитру, области и подписи.
Экспортированный `.schematic` можно открыть обычным интерфейсом Schematica.
Для переноса планов через экспорт агент читает исходные JSON и повторяет `schematic_put`
с новым scope без прежних planId/revision. Для обычного повторного входа достаточно Restore saved plans.

Пример разметки: площадка 9×7 с проходом другого цвета. Замените scope и координаты
на полученные из игры значения.

```json
{
  "session": "from-schematic_status", "dimension": 0,
  "name": "Площадка машин с центральным проходом",
  "x": 100, "y": 64, "z": 200,
  "width": 9, "height": 3, "length": 7,
  "palette": [
    {"block": "minecraft:stone", "meta": 0, "label": "Пол"},
    {"block": "minecraft:wool", "meta": 4, "label": "Проход, условная разметка"}
  ],
  "boxes": [
    {"x1": 0, "y1": 0, "z1": 0, "x2": 8, "y2": 0, "z2": 6, "palette": 0},
    {"x1": 4, "y1": 0, "z1": 0, "x2": 4, "y2": 0, "z2": 6, "palette": 1}
  ]
}
```

Координаты областей локальные и включают обе границы. Поздние области заменяют
ранние. Незаполненные клетки — воздух. Индекс `palette` начинается с нуля.
`schematic_put` возвращает `data.result.planId` и `revision`. Для замены передайте
оба значения и полный новый план; некорректная палитра сохраняет предыдущий план.
Для перемещения в `schematic_display` задайте все три координаты `x/y/z`.

Блок задаётся registry name и metadata 0–65535. Расширенная metadata GTNH
сохраняется в мире схемы, ведомости материалов и JSON без обрезания до четырёх бит.
Например, рама GregTech: `{"block":"gregtech:gt.blockframes","meta":300}`.
Значение нужно брать из установленной сборки; damage произвольного предмета
не обязательно является metadata блока. Машина GregTech задаётся так:

```json
{"block": "gregtech:gt.blockmachines", "machineId": 123, "facing": 2, "label": "Имя машины из реестра"}
```

`123` — пример формата, **не рекомендация конкретной машины**. Реальный ID нужно
получить из `gt_list_machines` / `gt_get_machine` установленной сборки.
`facing`: 0 вниз, 1 вверх, 2 север, 3 юг, 4 запад, 5 восток. Metadata основы
вычисляется по реестру GT; одновременно с `machineId` её передавать нельзя.
Экземпляры машин создаются только в отдельном мире схемы; игровые тики им не назначаются.
Для неокрашенных машин в NBT задаётся сырой `mColor:0b`; публичное значение
цвета `-1` нельзя записывать в это поле: у люков это приводит к неверному индексу текстуры.

Трубы и кабели GT используют тот же `machineId` из реестра. Основы 4–15 больше
не отклоняются. `connections` — маска сторон: вниз 1, вверх 2, север 4, юг 8,
запад 16, восток 32; например, `48` задаёт прямую трубу запад–восток.
Без маски видимые соединения строятся к соседним клеткам GT. Это геометрическая
разметка: совместимость материалов, типов труб и портов машин не проверяется.

Трубы и другие tile entity блоки модов задаются registry name, `meta` и `tileNbt`:
строкой SNBT длиной до 8192 символов, содержащей реальные данные конкретного мода.
Имена полей типа трубы и соединений зависят от мода; их нужно получить из реального
образца, а не угадывать. Локальные `x/y/z` задаёт адаптер, данные каждой клетки
копируются отдельно. Эти данные также сохраняются при экспорте. Поддержка передачи
NBT не гарантирует совместимость любого нестандартного рендера: некоторые моды
требуют тиков или отдельного клиентского кэша.

## Виджет Harness и callbacks

После создания плана агент выводит **отдельный** блок с языком
`minecraftagenttools:schematic-v1` рядом с объяснением этой схематики:

```json
{
  "session": "from-schematic_status",
  "dimension": 0,
  "world": "64-character-world-key-from-schematic_status",
  "persistentId": "from-this-plan-schematic_put-result-or-schematic_list"
}
```

Для двух схем нужны два блока с разными `persistentId`. Карточка показывает только
свой план: имя, путь группы, текстурное изометрическое 3D-превью, размеры, координаты,
Show/Hide и материалы. Добавление других схем не меняет её содержимое. Замена плана
сохраняет привязку и обновляет карточку; удаление оставляет сообщение о недоступной схеме.
Совпадение имён, групп или координат не перепривязывает карточку к другой схеме.
`group` остаётся организацией данных и подписью в карточке; общего дерева и массовых
кнопок Show/Hide в виджете больше нет.

Материалы встроены в карточку как компактная легенда: иконка предмета и точное
необходимое количество. Локализованное название из текущего языка игры появляется
при наведении на иконку или число. Названия registry/metadata и заданный агентом label
не заменяют локализованное имя. Длинная легенда листается собственными стрелками;
каждый экземпляр карточки хранит свою страницу. Тултип рисуется после чата и учитывает
его clipping при определении наведённого материала; изменения API Harness не требуются.

Числа обновляются вместе с планом и не зависят от его видимости. Легенда считает
полную схему после перекрытия boxes, без воздуха; она не вычитает построенные блоки
и не раскрывает рецепты. Одинаковые registry name + meta или machineId объединяются
независимо от label/facing/connections; разные tileNbt считаются отдельными вариантами.
Разбор текста не создаёт, не загружает и не переключает планы. Действие исполняется
только по явному нажатию. Обработчик повторно проверяет session/dimension, наличие
текущего planId и layout revision. Несколько карточек одной схемы читают одну актуальную
видимость, но имеют независимые страницы материалов и состояние ошибок превью.

`persistentId` — постоянный идентификатор схемы для карточки. Он возвращается в
put/get/list, переживает замену и восстановление и сохраняется локально. Для команд
по-прежнему нужны текущие `session`, `planId` и `revision`; постоянный идентификатор
не делает старые callbacks действительными. Старый формат `minecraftagenttools:schematics-v1`
без идентификатора поддерживает только восстановление сохранений и подсказку запросить
отдельные карточки. Он не выбирает первую или единственную схему автоматически.

Виджет реализован **в этом проекте**, в `harness-schematica-1.7.10`. Контракт
Harness остаётся общим: `WidgetCanvas.button(..., Runnable callback)` позволяет
другим модам назначать собственную Java-логику. Для текстурных превью требуется обновлённый Harness с `WidgetCanvas.custom(...)`.
Это общий callback рисования доверенного Java-мода: координаты переводятся в абсолютные,
область пересекается с clipping карточки/чата, native-host сохраняет и восстанавливает
GL-состояние и матрицы и очищает глубину только внутри области. Переносимый host может
вернуть false без вызова рендера. Вся логика Schematica остаётся в этом проекте;
API_VERSION остаётся 1 (добавление совместимого API).
Расширение исключено из обычной сборки. Для его включения нужен явно указанный
compile-only dev JAR Harness, собранный отдельно:

```powershell
.\gradlew.bat build "-PharnessApiJar=C:/path/to/harness-dev.jar"
```

При наличии этого параметра Gradle включает `harness-schematica-1.7.10`, а `bundle`
добавляет JAR в `harness-mods`. Без параметра ни соседний проект, ни его JAR не нужны.
Автоматической сборки/копирования соседнего проекта нет.

## Сохранение и восстановление после входа

После создания, замены, перемещения, удаления, Show/Hide или выбора слоя адаптер
автоматически сохраняет текущее дерево в `config/minecraftagenttools/schematics/<world>.json`
в каталоге игры. Сохраняются имена, группы, координаты, полные палитры и boxes, machineId,
направления, connections, tileNbt, видимость и выбранный слой. Удаление плана удаляет его
и из сохранения. Страница легенды остаётся состоянием отдельного экземпляра карточки.

После повторного входа откройте сохранённую карточку чата и нажмите **Restore saved plans**.
Призраки до нажатия не создаются. Кнопка загружает весь сохранённый набор и подключает
эту карточку к её схеме по `persistentId` в новой сессии. Остальные старые карточки требуют отдельного явного
нажатия для перепривязки; повторные нажатия не дублируют планы. Старые planId,
revision и callbacks не становятся действительными: агент заново читает status/list.
Восстановление сохраняет Hide/Show и слой; ранее скрытые схемы остаются скрытыми.
Старые файлы сохранений без `persistentId` получают разные идентификаторы при загрузке
и записывают их при восстановлении; повреждённые и повторяющиеся идентификаторы отклоняются.

В JSON карточки передавайте `world` из `schematic_status`: это непрозрачный ключ мира и
измерения. Для старых карточек с session/dimension сохраняются соответствия прежних
сессий (до 4096 на мир/измерение); новые карточки с world от этого лимита не зависят.
`schematic_status` и `schematic_list` возвращают `savedPlans`, `restoreRequired`,
`storageLoading`, `storageError`. Пока файл читается, редактирование ждёт; если есть
не восстановленный набор, редактирование требует сначала нажать Restore, чтобы не
затереть сохранение пустой сессией. При ошибке чтения/проверки файл не перезаписывается.

В одиночной игре ключ основан на каталоге установки, папке сохранения и seed мира;
на сервере — на адресе подключения. Измерения хранятся отдельно. Сервер не передаёт
надёжный постоянный ID мира: сброс мира на том же адресе неотличим от повторного входа,
поэтому загрузка всегда требует нажатия пользователя. Перенос установки/переименование
папки или смена адреса создают другой ключ; для переноса между ними используйте экспорт.

Чтение, сериализация JSON и запись выполняются отдельным упорядоченным потоком.
Запись сначала идёт во временный файл с flush, затем заменяет предыдущий; поддерживаемая
файловой системой атомарная замена используется при наличии. Серия изменений объединяется
до последнего снимка. В карточке отображается Saving plans до завершения записи.
При штатном закрытии клиент ждёт завершения очереди. Все вызовы Minecraft и создание
призраков остаются на клиентском потоке. До публикации восстановленного дерева строятся
все его призраки; ошибка блока/мода освобождает временные объекты и оставляет файл для
повторной попытки.

## Иерархия и данные для агента

В `schematic_put` доступно необязательное поле `group`, например `Завод/Энергетика`.
Путь содержит до четырёх непустых сегментов через `/`, суммарно до 128 символов.
Пустой или отсутствующий `group` размещает план в корне, в том числе при полной замене.
Группы — организация планов: путь группы не перемещает и не переключает схемы.
Идентификаторы и revisions остаются у отдельных планов. Агенту передаются инструкции
группировать связанные схемы и показывать отдельный виджет для каждого плана.

`schematic_list` сохраняет плоский `plans`, дополнительно возвращает `hierarchy`
с узлами `type: group` (`name`, `path`, `children`) и `type: plan`, а также общую
ведомость `materials`. Каждый план содержит `group` и собственную `materials` с `count`;
эти поля сохраняются в get и исходном JSON экспорта.

Превью использует отдельный мир схемы, стандартный RenderBlocks, текстуры атласа,
Forge render passes и специальные рендереры tile entities. Проекция ортографическая,
изометрическая; модель автоматически вписывается в область. Геометрия блоков кэшируется
в GL display lists и освобождается при замене/удалении плана и смене мира.
Превью показывает полную схему независимо от Show/Hide и выбранного слоя, не меняет
её положение, не запускает тики tile entities и не подключает принтер.
Сбой превью отмечается `3D error`, не отключая управление планом и ведомость.
Качество нестандартных рендереров модов требует проверки в игре.

## Ограничения и проверка

До 65536 клеток на план, 131072 суммарно, до 128 блоков на ось, 128 элементов
палитры, 256 областей и 262144 записей клеток за запрос. Tile entity — до 512 на план,
поддерживаются основы GT 0–15. Объекты рендерера создаются только в render callback,
кэшируются и освобождаются при удалении или смене мира. Контекст единственного
рендерера Schematica временно переключается для каждого плана и восстанавливается
в `finally`; активная схема пользователя и принтер к этим планам не подключаются.

Рендер блоков и tile entity получает текущие проходы Forge с восстановлением
прежних значений в `finally`; это требуется текстурам корпусов и машин GT.
Нет автоматической проверки работоспособности мультиблоков,
соединений труб/кабелей, пропускной способности, рецептов или энергообеспечения.
Агент должен объяснять допущения и легенду разметки. Экспорт содержит registry mapping,
metadata и данные созданных машин GT; положение и подписи остаются также в JSON.
Формат Alpha `.schematic` штатной Schematica обрезает metadata до 0–15 при чтении.
Поэтому экспорт плана с большей metadata явно отклоняется, чтобы не повредить
варианты блоков. Полный JSON такого плана можно получить через `schematic_get`;
автосохранение и отображение расширенной metadata от экспорта не зависят.

Регрессии люков и рам проверяются изолированно задачами
`:forge-schematica-1.7.10:test` и `:schematica-tools:test`: неверный сырой цвет
люка и отказ `meta:300` воспроизведены тестами до исправления. Дополнительно
проверены хранение 300/65535 поверх четырёхбитного хранилища Schematica,
замена блока со сбросом metadata и явный отказ экспорта вместо потери данных.

Проверены сборка, контракты, порядок областей, ограничения, сессии, независимая
видимость нескольких планов, сохранение предыдущей схемы при ошибке и загрузка
провайдера только из JAR. В Harness проверены callbacks, clipping и клики в ленте/деталях.
Живой запуск с этими модами проверен до главного меню GTNH: см.
[проверку запуска](startup-check.md). Отрисовка Schematica, текстуры и экспорт/импорт
машин GT в игре **не проверены**.
Ручная проверка: создать два непересекающихся плана, показать обе схемы, переключить
каждую кнопкой, выбрать слой, проверить направление машины, экспортировать и открыть
файл, сменить мир/измерение и убедиться, что старые карточки неактивны.

Профиль API:
[Schematica](https://github.com/GTNewHorizons/Schematica/tree/1.12.6-GTNH),
[GT BaseMetaTileEntity](https://github.com/GTNewHorizons/GT5-Unofficial/blob/5.09.54.183/src/main/java/gregtech/api/metatileentity/BaseMetaTileEntity.java).

Изолированные проверки: общие предки и перенос групп при revision replacement,
лимит 32 планов и общий объём, подсчёт после overwrite/air, объединение материалов с
разными label и facing, различие meta/machineId. Для отдельных виджетов проверены
независимые Show/Hide и страницы материалов, синхронизация двух карточек одной схемы,
