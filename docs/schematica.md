# Планы строительства через Schematica

Агент создаёт схемы с нуля: пол, проходы, группы машин, резерв под расширение.
Каждый план имеет своё имя, начало координат, палитру и набор прямоугольных областей.
До восьми планов отображаются одновременно; пользователь строит по призрачным блокам.
Реальные блоки и инвентари эти инструменты не меняют, принтер не используется.

## Подключение

- `schematica-tools.jar` — отдельный провайдер в `plugins` внешнего MCP.
- `minecraft-agent-tools-schematica-forge-1.7.10-*.jar` — клиентский адаптер в `mods`
  рядом со Schematica GTNH. Профиль публичного API сверён с установленной `1.12.6-GTNH`.
- Необязательный `minecraft-agent-tools-schematica-harness-1.7.10-*.jar` — виджет
  в `mods` рядом с адаптером и Minecraft Harness с callbacks в `WidgetCanvas`.
  Самостоятельные провайдер и адаптер от Harness не зависят.
- В `config/minecraftagenttoolsschematica.cfg`: `bridge.port` по умолчанию 25579,
  приватный `bridge.token`. В окружении MCP: `MAT_SCHEMATICA_PORT` и
  `MAT_SCHEMATICA_TOKEN` с такими же значениями.

Java 8 контракт и адаптер не включают MCP-провайдер, Harness, Schematica, GregTech
или современный Gson. Внешнее ядро работает на Java 21. Игровые операции выполняются
на клиентском потоке, TCP — на рабочих потоках общего `game-bridge`.

## Инструменты

| Инструмент | Действие |
| --- | --- |
| `schematic_status` | Готовность, клиентские session/dimension, ограничения |
| `schematic_list` | Все планы текущего мира, revision, видимость, ошибки отрисовки |
| `schematic_put` | Создать план или целиком заменить существующий по planId/revision |
| `schematic_get` | Получить полный план для последующего редактирования |
| `schematic_display` | Видимость, начало координат или один локальный слой; `layer: -1` — все слои |
| `schematic_remove` | Удалить призрачный план |
| `schematic_export` | Сохранить `.schematic` и исходный `.json` в `schematics` рабочего каталога MCP |

Все инструменты после статуса требуют **собственные** `session` и `dimension`
Schematica; сессии Minecraft, NEI и GregTech взаимозаменяемыми не являются.
Смена мира/измерения отзывает планы и старые callbacks. Для сохранения работы между
сессиями экспортируйте план; исходный JSON содержит палитру, области и подписи.
Экспортированный `.schematic` можно открыть обычным интерфейсом Schematica.
Чтобы восстановить несколько управляемых планов, агент читает исходные JSON и
повторяет `schematic_put` с новым scope без прежних planId/revision.

Пример разметки: площадка 9×7 с проходом другого цвета. Замените scope и координаты
на полученные из игры значения.

```json
{
  "session": "from-schematic_status", "dimension": 0,
  "name": "Площадка машин с центральным проходом",
  "x": 100, "y": 64, "z": 200,
  "width": 9, "height": 3, "length": 7,
  "palette": [
    {"block": "minecraft:stone", "meta": 0, "label": "Пол"},
    {"block": "minecraft:wool", "meta": 4, "label": "Проход, условная разметка"}
  ],
  "boxes": [
    {"x1": 0, "y1": 0, "z1": 0, "x2": 8, "y2": 0, "z2": 6, "palette": 0},
    {"x1": 4, "y1": 0, "z1": 0, "x2": 4, "y2": 0, "z2": 6, "palette": 1}
  ]
}
```

Координаты областей локальные и включают обе границы. Поздние области заменяют
ранние. Незаполненные клетки — воздух. Индекс `palette` начинается с нуля.
`schematic_put` возвращает `data.result.planId` и `revision`. Для замены передайте
оба значения и полный новый план; некорректная палитра сохраняет предыдущий план.
Для перемещения в `schematic_display` задайте все три координаты `x/y/z`.

Обычный блок задаётся registry name и metadata 0–15. Машина GregTech задаётся так:

```json
{"block": "gregtech:gt.blockmachines", "machineId": 123, "facing": 2, "label": "Имя машины из реестра"}
```

`123` — пример формата, **не рекомендация конкретной машины**. Реальный ID нужно
получить из `gt_list_machines` / `gt_get_machine` установленной сборки.
`facing`: 0 вниз, 1 вверх, 2 север, 3 юг, 4 запад, 5 восток. Metadata основы
вычисляется по реестру GT; одновременно с `machineId` её передавать нельзя.
Экземпляры машин создаются только в отдельном мире схемы; игровые тики им не назначаются.

Трубы и кабели GT используют тот же `machineId` из реестра. Основы 4–15 больше
не отклоняются. `connections` — маска сторон: вниз 1, вверх 2, север 4, юг 8,
запад 16, восток 32; например, `48` задаёт прямую трубу запад–восток.
Без маски видимые соединения строятся к соседним клеткам GT. Это геометрическая
разметка: совместимость материалов, типов труб и портов машин не проверяется.

Трубы и другие tile entity блоки модов задаются registry name, `meta` и `tileNbt`:
строкой SNBT длиной до 8192 символов, содержащей реальные данные конкретного мода.
Имена полей типа трубы и соединений зависят от мода; их нужно получить из реального
образца, а не угадывать. Локальные `x/y/z` задаёт адаптер, данные каждой клетки
копируются отдельно. Эти данные также сохраняются при экспорте. Поддержка передачи
NBT не гарантирует совместимость любого нестандартного рендера: некоторые моды
требуют тиков или отдельного клиентского кэша.

## Виджет Harness и callbacks

После создания планов агент может вывести блок с языком
`minecraftagenttools:schematics-v1` и JSON scope:

```json
{"session": "from-schematic_status", "dimension": 0}
```

Карточка показывает текущие планы и кнопки Show/Hide. Разбор текста не создаёт,
не загружает и не переключает планы. Действие исполняется только по явному нажатию.
Обработчик проверяет мир/измерение, наличие planId и layout revision повторно.
Список читается заново при отрисовке, поэтому отдельные карточки видят одинаковую
актуальную видимость. Старые карточки не перепривязываются к новому миру.

Виджет реализован **в этом проекте**, в `harness-schematica-1.7.10`. Контракт
Harness остаётся общим: `WidgetCanvas.button(..., Runnable callback)` позволяет
другим модам назначать собственную Java-логику. API_VERSION остаётся 1.
Сборка интеграции использует compile-only dev JAR Harness, который надо собрать
отдельно; другой путь задаётся `-PharnessApiJar=C:/path/to/harness-dev.jar`.
Автоматической сборки/копирования соседнего проекта нет.

## Ограничения и проверка

До 65536 клеток на план, 131072 суммарно, до 128 блоков на ось, 128 элементов
палитры, 256 областей и 262144 записей клеток за запрос. Tile entity — до 512 на план,
поддерживаются основы GT 0–15. Объекты рендерера создаются только в render callback,
кэшируются и освобождаются при удалении или смене мира. Контекст единственного
рендерера Schematica временно переключается для каждого плана и восстанавливается
в `finally`; активная схема пользователя и принтер к этим планам не подключаются.

Рендер блоков и tile entity получает текущие проходы Forge с восстановлением
прежних значений в `finally`; это требуется текстурам корпусов и машин GT.
Нет автоматической проверки работоспособности мультиблоков,
соединений труб/кабелей, пропускной способности, рецептов или энергообеспечения.
Агент должен объяснять допущения и легенду разметки. Экспорт содержит registry mapping,
metadata и данные созданных машин GT; положение и подписи остаются также в JSON.

Проверены сборка, контракты, порядок областей, ограничения, сессии, независимая
видимость нескольких планов, сохранение предыдущей схемы при ошибке и загрузка
провайдера только из JAR. В Harness проверены callbacks, clipping и клики в ленте/деталях.
Живой запуск с этими модами проверен до главного меню GTNH: см.
[проверку запуска](startup-check.md). Отрисовка Schematica, текстуры и экспорт/импорт
машин GT в игре **не проверены**.
Ручная проверка: создать два непересекающихся плана, показать обе схемы, переключить
каждую кнопкой, выбрать слой, проверить направление машины, экспортировать и открыть
файл, сменить мир/измерение и убедиться, что старые карточки неактивны.

Профиль API:
[Schematica](https://github.com/GTNewHorizons/Schematica/tree/1.12.6-GTNH),
[GT BaseMetaTileEntity](https://github.com/GTNewHorizons/GT5-Unofficial/blob/5.09.54.183/src/main/java/gregtech/api/metatileentity/BaseMetaTileEntity.java).
